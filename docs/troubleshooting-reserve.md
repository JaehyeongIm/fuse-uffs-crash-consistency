# 트러블슈팅: 예비 페이지 / 예비 블록 부재로 인한 read 오류

**작성일**: 2026-03-31
**작성자**: 임재형
**관련 파일**: `src/flash.h`, `src/file.c`, `src/gc.c`

---

## 1. 문제 발생 — read 테스트 오류

통합 테스트(`test_integration.cpp`)의 파일 읽기 TC에서 기대값과 다른 데이터가 반환되는 오류가 발생했다.

**재현 조건**:
- 파일에 데이터를 append만 하여 블록 전체를 채운 상태 (무효 페이지 없음)
- 이후 overwrite(수정) 요청 발생

---

## 2. 원인 분석

### 2.1 코드 구조 (수정 전)

```c
// flash.h (수정 전)
#define FILE_HEADER_DATA_PAGES  31  // page 0(헤더) + page 1~31(데이터) = 32칸 전부 사용

// gc.c (수정 전)
int new_blk = flash_alloc_block();  // GC 복사 목적지를 일반 할당 풀에서 가져옴
```

### 2.2 버그 1 — GC 후 새 블록도 꽉 참 (예비 페이지 부재)

append만 하여 블록을 채운 경우 무효 페이지가 없다.

```
FILE 블록 (block 5):
p0:  헤더    [유효]
p1:  데이터  [유효]
...
p31: 데이터  [유효]  ← 32칸 전부 유효, 무효 페이지 0개
```

이 상태에서 p1 overwrite 요청 시:

```
flash_alloc_page(block 5) → 빈 슬롯 없음
    ↓
gc_collect_block(block 5) 호출
    → 유효 32개 전부 새 블록에 복사
    → 새 블록도 32칸 전부 꽉 참  ← 빈 슬롯 없음
    → block 5 erase
    ↓
flash_alloc_page(새 블록) → 또 빈 슬롯 없음
    ↓
gc_collect_block() 다시 호출 → 무한 반복 → -ENOSPC
    ↓
write 실패 → read 시 구버전 데이터 반환 → 테스트 오류
```

**핵심**: GC는 유효 페이지를 전부 복사한다. 무효 페이지가 없으면 복사 후에도 새 블록이 꽉 차서 CoW를 위한 빈 슬롯이 생기지 않는다.

### 2.3 버그 2 — GC 자체가 실행 불가 (예비 블록 부재)

플래시 전체에 빈 블록이 없는 상황에서 GC를 호출하면:

```
gc_collect_block(block 5):
    ↓
flash_alloc_block()  // 복사 목적지 블록 필요
    → 플래시 전체에 빈 블록 없음 → -ENOSPC
    ↓
GC 실패 → write 실패
```

GC가 실행되려면 빈 블록이 필요한데, 빈 블록이 없는 것이 GC 트리거 조건이므로 서로가 서로를 기다리는 데드락이 발생한다.

---

## 3. 해결 방법

### 3.1 예비 페이지 도입 (버그 1 해결)

```c
// flash.h (수정 후)
#define FILE_HEADER_DATA_PAGES  30  // page 1~30 = 데이터, page 31 = CoW 예비 슬롯
```

블록 내 page 31을 데이터 영역에서 제외하여 항상 비워둔다.

**GC 후 새 블록 상태 변화**:

```
수정 전: 유효 32개 복사 → 새 블록 32칸 전부 꽉 참 → 빈 슬롯 없음
수정 후: 유효 최대 31개 복사 → 새 블록 q31 항상 빔 → CoW 즉시 가능
```

GC 완료 직후 q31이 비어있으므로 write가 바로 q31에 신버전을 기록할 수 있다.

**GC 후 write 흐름**:

```
GC 완료 직후:
q0~q30: 유효 (31개 복사됨)
q31: 빈  ← write를 위한 슬롯

write 실행:
q31에 p1 신버전 기록
q1(구버전) 무효화 (dirty 1→0)

write 완료 후:
q1:  무효 ← 다음 CoW를 위한 빈 슬롯으로 전환
q31: 유효 (신버전)
```

예비 슬롯은 q31 → q1으로 이동하여 다음 수정 요청에서도 빈 슬롯이 보장된다.

### 3.2 Rolling Spare Block 도입 (버그 2 해결)

```c
// flash.h
#define GC_SPARE_BLOCK  (TOTAL_BLOCKS - 1)  // block 127을 GC 전용으로 예약

// gc.c (수정 후)
int new_blk = flash_get_gc_spare();  // 일반 할당 풀과 분리된 전용 예비 블록 사용
```

GC 전용 예비 블록을 일반 할당 풀(`flash_alloc_block`)과 완전히 분리한다.

**Rolling Spare 동작**:

```
GC 전:  spare=block127(빈),  victim=block5(유효)
    ↓
block5 live 페이지 → block127에 복사
block5 erase
flash_set_gc_spare(block5)  // erase된 block5가 새 spare
    ↓
GC 후:  spare=block5(빈),   block127=데이터(복사됨)
```

플래시 전체에 빈 블록이 0개여도 spare 블록이 항상 1개 별도로 확보되어 있으므로 GC가 실행 가능하다.

---

## 4. 두 해결책의 관계

두 버그는 같은 상황(공간 부족)에서 다른 레벨로 발생한다.

| 버그 | 발생 레벨 | 해결책 |
|------|---------|--------|
| 버그 1 (예비 페이지 부재) | 블록 내 페이지 레벨 | page 31 예약 |
| 버그 2 (예비 블록 부재) | 플래시 전체 블록 레벨 | Rolling Spare Block |

버그 2만 해결하면: GC는 실행되지만 새 블록도 꽉 차서 무한 반복
버그 1만 해결하면: 새 블록에 빈 슬롯이 생기지만 GC 자체가 실행 불가

두 가지를 함께 적용해야 완전히 해결된다.

## 5. 오해하기 쉬운 포인트

### Q. GC 시 수정 요청된 구버전 페이지를 제외하고 복사하면 되지 않나?

GC와 write는 실행 시점이 다르다. GC가 호출되는 시점에는 아직 write가 실행되지 않았으므로 구버전이 유일한 유효 페이지다. 구버전을 제외하고 복사하면 데이터가 손실된다.

또한 GC에 write 내용을 넘겨 통합하는 방식은 가능하지만, GC(공간 확보)와 write(데이터 기록)의 역할 분리가 깨져 구현 복잡도가 높아지고 Crash Consistency 보장이 어려워진다.

### Q. 예비 페이지가 있으면 무효 페이지가 반드시 1개 있으니 GC 후 1칸이 남는 것 아닌가?

무효 페이지 유무와 무관하다. page 31은 코드 상에서 데이터 슬롯으로 절대 할당하지 않는다. GC 시 최대 복사 개수가 31개(p0~p30)로 구조적으로 제한되어 있기 때문에 새 블록의 q31은 항상 비어있다.

### Q. "1칸이 남는다"는 것이 write 완료 후를 의미하는가?

아니다. GC 완료 직후, write 실행 전 시점이다. write 완료 후에는 q31이 신버전으로 채워지고, 대신 구버전 q1이 무효화되어 다음 CoW를 위한 빈 슬롯이 된다.

### Q. GC 도중 크래시가 발생하면 예비 페이지와 관계없이 정합성이 깨지지 않나?

GC는 "복사 완료 → 구 블록 erase" 순서로 실행된다. 복사 도중 크래시가 나도 구 블록은 건드리지 않았으므로 remount 시 구 블록이 그대로 복원된다. erase 도중 크래시는 `tree_build` Phase 0(불완전 erase 복구)에서 처리한다. 예비 페이지는 Crash Consistency와 무관하고 오직 "GC 후 CoW 가능한 빈 슬롯 보장"이 목적이다.

### Q. 무효 페이지가 많은 파일이면 GC로 빈 블록을 만들 수 있지 않나?

`gc_collect_block()`은 블록 1개 단위로만 처리한다. GC 후 victim 블록은 erase되지만 rolling spare로 전환되어 `flash_alloc_block()`이 반환하지 않는다. 실제로 새 파일 할당에 쓸 수 있는 빈 블록이 생기는 경우는 Pass 1(유효 페이지 0개인 블록 즉시 erase)뿐이다.

여러 블록에 파편화된 유효 페이지를 하나로 합쳐 빈 블록을 확보하는 압축(compaction) 기능은 현재 구현되어 있지 않다. 이는 SRS FR-FILE-004-3(선제적 GC)으로 미구현 항목으로 남아있다. 현재는 공간이 완전히 소진된 시점에 on-demand로만 GC가 트리거된다.
